# Architecture and design notes

## Boundaries

`main.py` owns HTTP parsing, authentication and lifecycle. Synchronous route functions run in FastAPI's worker thread pool, matching the synchronous SDKs. `Services` owns use cases. The `LanguageModel` protocol separates model integration from orchestration. `VectorStore`, `ChatMemory` and SQLAlchemy handle their own storage concerns. Pydantic schemas validate API and LLM contracts.

The application starts its clients once, verifies Redis and Qdrant, and closes resources on shutdown. Tests inject complete services into the same app factory. Environment secrets are never committed. Logging records exception types rather than user message bodies or raw provider responses.

## Ingestion consistency

1. Validate and extract the document before creating a SQL record.
2. Commit `pending` metadata.
3. Embed in batches of 32, then upsert Qdrant points in batches of 64.
4. Commit chunk metadata and `ready` status in one SQL transaction.
5. On failure, mark `failed` and attempt to delete the document's vectors.

Every search checks that all supplied document IDs have `ready` SQL records with matching embedding configuration. There is no distributed transaction across SQLite and Qdrant. A sudden process termination can leave `pending` rows or orphan vectors. A production reconciliation worker should remove stale pending vectors or retry ingestion from durable originals. This demo does not retain the original uploads.

## Retrieval

The API requires explicit `document_ids` on each question. Omitted IDs produce an instruction to upload/select a document; it never silently searches all documents. The same embedding model produces document and question vectors. Qdrant filters on document IDs, uses cosine similarity and returns at most five hits above a default threshold of 0.25. Both settings are configurable and must be tuned using representative data.

The planner sees only the user's current message, bounded history and draft state. Retrieved documents never enter the booking planner. The answer model receives a standalone question and retrieved text, with instructions treating text as untrusted evidence. Source indices are checked against actual hits; invalid or missing source indices cause a supported-answer fallback. Source validation proves the reference exists, not semantic entailment of every generated statement.

## Conversation state and replay

Normal conversational history and booking drafts are read from Redis. Keys are namespaced by a UUID session ID and expire after inactivity. A five-minute Redis lock serializes requests to the same session; a competing request receives 409 after waiting up to two seconds. Each chat uses at most three sequential model calls with 30-second network timeouts and disabled automatic retries. A lock lease is not a hard wall-clock deadline; a stalled process or streaming/trickle network failure could outlive it. SQL uniqueness still protects replay keys and exact booking slots.

After computation, the response and a bounded state snapshot are persisted to `chat_turns`. A confirmed booking is saved in the same SQL transaction. Redis is refreshed after the SQL commit. If Redis fails at that point, the caller retries the identical request ID and payload. The response is replayed from SQL and the newest session snapshot is restored to Redis. Replaying an older request never rewinds Redis to that older state.

A request ID cannot be reused with a different payload. New request IDs mean new operations; they are not fuzzy deduplication. Clients should finish retrying a failed request before advancing the conversation.

SQL replay records contain chat snapshots and can contain personal details. Redis TTL is not deletion from SQL. This assignment leaves SQL retention explicit as an operational follow-up, rather than claiming all conversation data expires after 24 hours.

## Booking semantics

The model returns typed intent and nullable fields. Only supplied fields update the current draft. Four fields are required: name, email, date and time. Pydantic validates structure and values; application code rejects past timestamps and ambiguous/nonexistent daylight-saving times. The configured timezone appears in the confirmation and saved result.

Any change to displayed details resets confirmation. The backend only saves when an unchanged valid draft was already awaiting confirmation and the current plan identifies an explicit confirmation. The response's booked status is generated by application code after an actual database write.

A unique UTC start timestamp models one interviewer. There is no duration model or interval-overlap check. A collision is handled inside a SQL savepoint, allowing the conversation's “choose another time” response to be committed. SQLite uses explicit BEGIN events so savepoint release cannot accidentally commit a booking outside the outer chat transaction on Python 3.11.

## Error contract

| Status | Meaning |
| --- | --- |
| 201 | Document fully ingested and ready |
| 200 | Chat response, including questions for missing/invalid booking fields |
| 401 | Missing or incorrect shared API key |
| 404 | At least one requested document is missing or not ready |
| 409 | Session busy, replay payload mismatch or embedding configuration mismatch |
| 413 | Uploaded file exceeds configured byte limit |
| 422 | Invalid request fields, unsupported document, bad extraction or chunk settings |
| 503 | Dependency or unhandled application failure; chat may be safely retried with the same ID |

The broad final error handler intentionally avoids leaking internals, but does not classify every possible provider failure separately. Production observability should distinguish authentication, throttling, network and internal errors without exposing secret or personal data.
